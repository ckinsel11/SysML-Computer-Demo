Use Cases for Continuous System Integration (CSI) Pipelines:
    1. Style Guide Checks
        What are we monitoring? 
            The entire repository
        What is the pipleline doing?
            It will check every file against a set of "coding standard rules" that are pre-defined. This could be as simple as definitions need to have documentation, to properties being typed and having units when necessary. 
        What about built-in validation rules?
            The value here is that this prevents any conflicts with personal configurations of an IDE or any development environment factors. For example, for sysml v1 i set auto-validation basically to never run due to performance issues and other annoyances. This means i could miss something critical that affects the model "quality" where as having a pipeline run everything on a neutral machine, there is a "known" environment to compare everything against. Tools like cameo and syside can do some of this and provide a great first-line of defense but again running everything again through a pipeline ensures better accuracy and accounting of any issues that get through. We are all human after-all.
    2. Design "Verification"
        What are we monitoring?
            Some specific files/maybe the entire repository
        What is the pipeline doing?
            Basically checking the design against all of the known constraints/design restrictions and rules to verify we have a valid design.
            *This is especially important for Technical Performance Measures (TPMs) the program is tracking.*
    3. Artifact Generation
        What are we monitoring?
            The entire repository
        What is the pipeline doing?
            It is using our files and documentation to generate all of the views needed for all of our artifacts/cdrls and then generating those artifacts.
    4. Analysis Kick-Off 
        What are we monitoring?
            Specific file(s)
        What is this pipeline doing?
                It is checking a particular file that we will use to kick of an analysis of the design space. For an aoa, we could change our options, commit, and then a pipeline would see those changes and start the pipeline for the automatic evalutions.
                *This is especially important for Technical Performance Measures (TPMs) the program is tracking.*
    5. Data "Integration" 
        What are we monitoring?
            Specific file(s)
        What is the pipeline doing?
            Taking data from the architecture description and putting in into a known location for another tool to ingest. Essentially an Extract/Transform/Load
